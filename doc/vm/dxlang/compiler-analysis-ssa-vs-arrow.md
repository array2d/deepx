# `->`/`<-` 与 SSA 编译器分析能力对比

> **核心问题**：deepxir 的 `->`/`<-` 读写分离模型，能否在不引入完整 SSA 的前提下，支持经典编译器的全部分析和优化 pass？
> **结论**：是。通过**变量版本号编码控制流合流**，以零语法增量获得等同 SSA 的完整分析能力。

---

## 1. 问题定义

```
给定一个 ->/<- 形式的 deepxir 函数:

  fn example(flag: bool, a: f32, b: f32) -> y: f32 {
    a + b -> t
    if flag {
      t * 2.0 -> x
    } else {
      t + 3.0 -> x
    }
    x + 1.0 -> y          # 写入输出参数 y 即隐式返回
  }

目标: 在不转换为完整 SSA (不引入 block argument、φ 节点、CFG 基本块) 的前提下:

  Q1: 死代码消除 — t 的值在 if/else 之后是否还被使用？
  Q2: 公共子表达式消除 — 两处相同的 a+b 能否识别并消除？
  Q3: 常量传播 — 条件常量能否跨分支传播？
  Q4: 全局值编号 — 能否为跨分支的值分配唯一编号？
  Q5: 循环不变量外提 — 能否识别和移动循环不变量？
  Q6: 寄存器分配 — 能否构建精确的干涉图？
```

## 2. 两种模型的本质差异

```
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  SSA  = 值身份模型 (Value Identity)                        │
│         每个变量有唯一静态定义点                             │
│         追踪"哪个值"被使用                                  │
│         use-def 链: 从使用点 O(1) 回溯到唯一定义点          │
│         控制流合流: block argument / φ 节点                │
│         典型系统: LLVM IR, MLIR, GCC GIMPLE                │
│                                                            │
│  ->/<- = 存储效应模型 (Storage Effect)                     │
│          变量是可复用的存储槽位                             │
│          追踪"哪个存储位置"被读写                           │
│          数据流: reads[] / writes[] 数组显式标注           │
│          控制流合流: slot 复用 (同名字覆盖)                │
│          典型系统: deepxir                                 │
│                                                            │
│  核心分歧: SSA 关心"值的身份"，->/<- 关心"存储的效应"。     │
│  两者服务不同层次，不是替代关系，是互补关系。               │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

| 维度 | SSA | `->`/`<-` |
|------|-----|----------|
| **变量赋值次数** | 严格 1 次 | 无限次（可变） |
| **值标识** | 虚拟寄存器编号 (`%0`, `%1`) | KV 路径 (`./x`, `/data/W`) |
| **数据流表达** | 操作数引用 = 隐式 use-def 链 | 显式 reads[] / writes[] 数组 |
| **控制流合流** | block argument / φ 节点 | slot 复用 (同名覆盖) |
| **副作用建模** | 需隔离到 dialect (memref) | 天然 (tensor.new/del 即指令) |
| **定义-使用关系** | 支配树保证: 定义支配所有使用 | 需额外分析 (到达定义) |
| **线形段等价性** | 等价 | 等价（可建立双射映射） |
| **控制流等价性** | 语义等价，结构不等价 | 语义等价，结构不等价 |

### 线形段的等价性

在无控制流分支的线性代码中，两者严格等价：

```
SSA:                              ->/<-:
  %0 = add %a, %b                   a + b -> t
  %1 = mul %0, 2.0                  t * 2.0 -> x
  %2 = add %1, 1.0                  x + 1.0 -> y       # 写入 y = 隐式返回
  ret %2

映射: 每个 SSA 虚拟寄存器 %i ←→ 首次出现在写位置的变量名
     SSA use ←→ 读位置的变量名
     双射关系: 线性段内完全一一对应
     deepxir 无 ret <value>: 写入输出参数即返回
```

### 控制流合流 — 两种模型的分岔点

```
场景: if/else 分支后使用结果

SSA (MLIR 风格):                   ->/<- (slot 复用):
  br flag ? @then : @else            if flag {
                                     a + 1.0 -> x
@then:                             } else {
  %t = add %a, 1.0                   a - 1.0 -> x
  br @merge(%t)                    }
                                   x * 2.0 -> y
@else:
  %e = sub %a, 1.0
  br @merge(%e)

@merge(%y: f32):        ← block arg
  %r = mul %y, 2.0
  ret %r

机制: block argument 参数化        机制: slot x 被两个分支复用
优势: SSA 贯穿始终                 优势: 零额外语法，VM 直接读 slot
代价: 需 CFG + block 分割          代价: 失去值身份，编译器分析困难
```

**核心矛盾**: SSA 为编译器分析而生 (值身份、use-def、支配树)，但改变了 IR 结构。
`->`/`<-` 为执行透明而生 (slot 复用、协议直通)，但丢失了值身份信息。

## 3. 逐个 Pass 可行性分析

### 3.1 无版本号（纯 slot 复用）下的能力

| Compiler Pass | 可行性 | 需要额外什么 | 精度损失 |
|---------------|--------|-------------|---------|
| **常量折叠** | ✅ 直接 | 无 | 无 |
| **死代码消除** | ⚠️ 可行 | 活性分析 O(n²) | 无 |
| **常量传播** | ⚠️ 可行 | 到达定义分析 | 轻微 |
| **复写传播** | ⚠️ 可行 | 到达定义检查 | 无 |
| **CSE** | ⚠️ 部分可行 | 到达定义 (线性段 O(n)，控制流 O(n²)) | 有（控制流） |
| **GVN** | ❌ 不可行 | 需先 SSA 构造 | — |
| **LICM** | ⚠️ 可行 | 到达定义 + 循环识别 | 无 |
| **SCCP** | ❌ 不可行 | 需支配树 + SSA 稀疏表示 | — |
| **寄存器分配** | ⚠️ 粗略可行 | 区分变量版本 (活性分析) | 有 |
| **归纳变量** | ✅ 可行 | 模式匹配 | 无 |
| **内联** | ✅ 可行 | 无 | 无 |

**关键观察**: 几乎所有"⚠️ 可行但需额外工作"的场景，额外工作 = **到达定义分析**。
而到达定义分析的结果 = **为每个 slot 的每次写入分配唯一标识** — 这就是在做 SSA 构造。

### 3.2 失败的根源：值身份的缺失

```
为什么纯 slot 复用下的 CSE 不可靠:

  add(a, b) -> t1      ← 定义 t1
  add(a, b) -> t2      ← 也是 add(a, b)！但 t1 == t2 ?
                        ← 不确定: a, b 在两指令间可能被重定义
                        ← 编译器必须做到达定义分析才能确认

为什么纯 slot 复用下的 GVN 不可行:

  GVN 的核心: "值相等"判断 → 需要"值"这个概念
  纯 slot 复用没有"值" — 只有"slot 的当前内容"
  "slot 的当前内容"随时间变化, 无法分配稳定的值编号

结论: 纯 slot 复用缺少一类关键信息——
      "此时 slot S 中存储的值是第几次写入产生的"。
      即: 缺少**值身份**。
```

## 4. 方案：变量版本号编码合流

### 4.1 核心思想

**给每次写入附加版本号后缀，控制流合流自动产生合并版本号。
版本号 = 值身份。合流版本 = 隐式 φ。**

```
规则:

1. 每个 slot 维护独立的版本计数器，从 0 开始
2. 每次写入 (-> 右侧): 产生新版本 slot/N
   读取 (-> 左侧): 使用当前可见版本的 slot
3. 控制流合流: 自动产生合并版本
   merge_ver = max(各分支最大版本, 合流前最新版本) + 1
   合并版本无需显式定义 —— 编译器自动识别
```

### 4.2 语法

```
# 线性代码
constant(3.0) -> a/0        # a 首次写入 → a/0
a/0 + 2.0 -> b/0            # 读 a/0, 写 b/0
b/0 * 4.0 -> c/0            # 读 b/0, 写 c/0

# 带分支
if flag {
  a/0 + 1.0 -> x/0          # 写 x/0
} else {
  a/0 - 1.0 -> x/1          # 写 x/1
}
# 合流: x 在两个分支写入，自动产生合并版本 x/2 = φ(x/0, x/1)
x/2 * 2.0 -> y/0            # 读合并版本 x/2, 写入输出参数 y/0 = 隐式返回
```

**VM 行为**: 版本号被 VM 完全忽略。VM 只看 slot 名 (`x`)，不看后缀 (`/2`)。
slot 复用语义保持不变 — 运行时 `x` 持有实际值，无论来自哪个分支。

### 4.3 编译器如何识别合流版本

```
判定规则:
  如果版本 S/N 在程序中被使用（读侧出现），
  但没有任何显式的 op(...) -> S/N 定义它，
  则 S/N 是合流版本。

算法:

  func resolve_merge(slot, version, point):
    if has_explicit_def(slot, version):
      return  // 运算版本，无需处理
    
    // 找到紧邻的前驱控制流结构
    cfg = preceding_control_flow(point)
    
    // 收集所有分支中 slot 的写入版本
    sources = []
    for branch in cfg.branches:
      defs = find_writes(slot, branch)
      if defs:
        sources.extend(defs)
      else:
        sources.append(slot_version_before_cfg(slot, cfg))
    
    // 构建内部 φ: slot/version = φ(sources...)
    // 所有后续分析在 φ 之上执行
    return create_phi(slot, version, sources)
```

### 4.4 嵌套控制流与循环

```
嵌套 if:
  a + 1.0 -> a/1
  
  if outer {
    if inner {
      a/1 * 2.0 -> a/2       # inner then
    } else {
      a/1 * 3.0 -> a/3       # inner else
    }
    # inner 合流: max(2,3)+1=4 → a/4 = φ(a/2, a/3)
    a/4 + 1.0 -> a/5
  } else {
    a/1 * 4.0 -> a/6         # outer else
  }
  # outer 合流: max(5,6)+1=7 → a/7 = φ(a/5, a/6)
  a/7 / 2.0 -> y/0

版本序列: a/1 → a/2/a/3 → a/4(inner φ) → a/5 → a/6 → a/7(outer φ) → y/0
完整记录所有分支与合流的数据流。


循环:
  0.0 -> acc/0
  for i in 0..100 {
    # 循环头合流: acc/1 = φ(acc/0, acc/3)
    #   首次迭代来自 acc/0
    #   后续迭代来自上次的 acc/3
    data[i] + acc/1 -> acc/2
    acc/2 + 1.0 -> acc/3
  }
  # 循环退出: acc/4 = φ(acc/0, acc/3)
  #   0 次迭代 → acc/0
  #   有迭代 → acc/3
  acc/4 -> total/0
    
说明: 循环合流需编译器识别循环结构 (for/while 关键字天然提供边界)。
      编译器追踪循环携带变量的跨迭代版本。
```

## 5. 完整编译器分析验证

### 5.1 死代码消除 (DCE)

```
if flag {
  a + 1.0 -> x/0
  b * 2.0 -> dead/0        ← 仅在 then 分支被定义
} else {
  a - 1.0 -> x/1
}
x/2 + 3.0 -> y/0           ← x/2 = φ(x/0, x/1), 写入 y/0 = 隐式返回

编译器分析:
  1. 扫描所有读侧: x/2 被使用, y/0 是输出参数 → 活
  2. dead/0 从未被读 → 死代码 → 删除
  3. x/2 是合流版本 → 其 φ 来源 x/0 和 x/1 都活
  4. 精确度等同 SSA 的 use-count DCE

结论: ✅ 完全支持, O(n) 版本 use 计数
```

### 5.2 公共子表达式消除 (CSE)

```
if flag {
  a + b -> x/0             ← add(a, b)
} else {
  a + b -> x/1             ← add(a, b) — 相同操作数和操作码!
}
x/2 * 2.0 -> y/0           ← x/2 = φ(x/0, x/1)

编译器分析:
  1. x/0 的定义: op=add, args=[a, b]
  2. x/1 的定义: op=add, args=[a, b]
  3. 操作数和操作码完全相同 → x/0 和 x/1 是同一值
  4. x/2 = φ(x/0, x/1) = φ(x/0, x/0) = x/0
  5. φ 退化为单一来源 → x/2 可替换为 x/0 或 x/1
  6. 消除 x/1 (else 分支直接用 x/0)

结论: ✅ 完全支持。版本号暴露操作数版本 → 直接比较
```

### 5.3 全局值编号 (GVN)

```
a + b -> t/0
c + d -> u/0
if flag {
  a + b -> x/0             ← VN = hash(add, a/0, b/0) = 42 (同 t/0)
} else {
  c + d -> x/1             ← VN = hash(add, c/0, d/0) = 17 (同 u/0)
}
x/2 + 1.0 -> y/0           ← x/2 = φ(42, 17) = hash(φ, 42, 17)

编译器分析:
  分配 VN:
    t/0 = 42
    u/0 = 17
    x/0 = 42  ← 与 t/0 相同 → 可互相替换
    x/1 = 17  ← 与 u/0 相同 → 可互相替换
    x/2 = φ(42, 17) → VN = hash(φ, 42, 17) = 99
    y/0 = hash(add, 99, 1.0)

结论: ✅ 完全支持。φ 的 VN 由来源 VN 唯一确定
```

### 5.4 稀疏条件常量传播 (SCCP)

```
constant(true) -> flag/0
if flag/0 {
  constant(5.0) -> x/0
} else {
  constant(3.0) -> x/1     ← 不可达! flag=true 永不走 else
}
x/2 + 1.0 -> y/0

编译器分析:
  1. all values = ⊤ (top, unknown)
  2. flag/0 = true → 常量
  3. if true → then 可达到, else 不可达
  4. then: x/0 = 5.0 → 常量
  5. else: 不可达 → x/1 = ⊥ (从未定义)
  6. x/2 = φ(x/0=5.0, x/1=⊥) = 5.0
     (不可达来源被忽略)
  7. y/0 = 5.0 + 1.0 = 6.0 → 常量

结论: ✅ 完全支持。精度等同 LLVM SCCP
```

### 5.5 循环不变量外提 (LICM)

```
a * b -> inv/0             ← 定义在循环外
0.0 -> acc/0
for i in 0..n {
  acc/1 = φ(acc/0, acc/3)  ← 循环合流
  inv/0 + acc/1 -> acc/2
  acc/2 + i -> acc/3
}

编译器分析:
  1. inv/0 定义在循环外
  2. 循环内无 inv 的新版本 (无 inv/1, inv/2...)
  3. → inv/0 是循环不变量
  4. 无需外提 (已在循环外)

结论: ✅ 完全支持。版本号直接暴露不变性
```

### 5.6 寄存器分配 / 干涉图

```
a + b -> t1/0
t1/0 * 2 -> t2/0
if flag {
  t1/0 + 5 -> t3/0
} else {
  t2/0 + 3 -> t3/1
}
t3/2 * t1/0 -> z/0        ← t3/2 = φ(t3/0, t3/1)

编译器分析:
  1. 活性区间:
     t1/0:  [1, 7]  (定义→最后使用)
     t2/0:  [2, 5]
     t3/0:  [4, 6]  (then 分支内)
     t3/1:  [5, 6]  (else 分支内)
     t3/2:  [7, 7]  (合流后)
  2. 干涉:
     t1/0 与 t3/2 干涉 (区间 [1,7] ∩ [7,7])
     t3/0 与 t3/1 不干涉 (不同分支，活性不重叠)
  3. 图着色: 精确分配寄存器

结论: ✅ 完全支持。版本号提供精确活性区间
```

## 6. 与纯 SSA 的架构对比

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  纯 SSA (MLIR cf dialect):                                      │
│                                                                 │
│  @0:                                                            │
│    %0 = add %a, %b                                              │
│    br %flag ? @1 : @2              ← 基本块分割                 │
│  @1:                                                            │
│    %1 = add %a, 2.0                                              │
│    br @3(%1)                       ← block argument 传递        │
│  @2:                                                            │
│    %2 = sub %a, 2.0                                              │
│    br @3(%2)                       ← block argument 传递        │
│  @3(%x: f32):                      ← %x = φ(%1, %2)            │
│    %3 = mul %x, 3.0                                              │
│    ret %3                                                        │
│                                                                 │
│  版本号编码合流 (deepxir):                                        │
│                                                                 │
│  fn example(flag: bool, a: f32) -> y: f32 {                     │
│    a + b -> x/0                                                  │
│    if flag {                                                     │
│      a + 2.0 -> x/1                                             │
│    } else {                                                      │
│      a - 2.0 -> x/2                                             │
│    }                                                            │
│    x/3 * 3.0 -> y/0             ← x/3 隐式 = φ(x/1, x/2)       │
│  }                                ↑ 写入输出参数 y/0 = 隐式返回  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

┌────────────────────────┬──────────────────────┬──────────────────────┐
│ 维度                    │ 纯 SSA               │ 版本号编码合流        │
├────────────────────────┼──────────────────────┼──────────────────────┤
│ IR 结构变化             │ 函数→基本块→指令     │ 函数→指令(一层)      │
│ 合流机制                │ block argument       │ 版本号隐式编码        │
│ 前端生成复杂度          │ 高 (CFG 构造 + φ)    │ 低 (版本计数器)      │
│ VM 执行                 │ 需 block-loop        │ slot 复用,零变化      │
│ 编译分析能力            │ 原生 SSA             │ 内部 SSA (自动构建)  │
│ 向后兼容                │ ❌ 不兼容现有 IR      │ ✅ 不加版本号照常运行 │
│ 人可读性                │ 编号 %0 %1 无意义    │ 名字有意义 + 版本可溯源│
│ 与执行协议对齐           │ 需 lower 到 slot     │ 直接 = slot 格式     │
└────────────────────────┴──────────────────────┴──────────────────────┘
```

## 7. 实现路线

```
Phase 1: 前端版本号计数器
  ┌─────────────────────────────────────────────┐
  │ 每个 slot 维护: slot → current_version       │
  │ 写入: ver = ++counter → 输出 "slot/ver"      │
  │ 读取: 使用 slot 当前可见版本                  │
  │ 合流: merge_ver = max(branch_versions) + 1   │
  │                                              │
  │ 新增代码量: ~100-200 行                      │
  │ VM: 0 行 (版本号被忽略)                      │
  └─────────────────────────────────────────────┘

Phase 2: 编译器合流识别
  ┌─────────────────────────────────────────────┐
  │ 解析 slot/ver 格式                           │
  │ 跟踪 slot→定义映射                           │
  │ 识别无显式定义的版本 → 标记为合流版本         │
  │ 从控制流结构反查来源 → 构建内部 φ             │
  │                                              │
  │ 新增代码量: ~200-300 行                      │
  └─────────────────────────────────────────────┘

Phase 3: 优化 Pass 全线启用
  ┌─────────────────────────────────────────────┐
  │ 内部 SSA 已就绪                               │
  │ 复用标准优化 pass (DCE, CSE, GVN, SCCP...)   │
  │ 优化结果映射回 slot → 输出优化后 IR           │
  │                                              │
  │ 优化 pass 本身: 标准实现,无需新代码           │
  └─────────────────────────────────────────────┘
```

```
│  A: 能。通过变量版本号编码控制流合流。                        │
│                                                              │
│  纯 slot 复用:                                               │
│    ❌ 缺少值身份 → 全局分析不可行                            │
│    ✅ 执行层高效 (VM 直接读写 slot)                          │
│                                                              │
│  版本号编码合流:                                              │
│    ✅ 线性段: slot/ver 直接提供 use-def 链, O(1)             │
│    ✅ 控制流合流: 编译器自动识别合流版本 → 构建内部 φ       │
│    ✅ 全部 pass: DCE, CSE, GVN, SCCP, LICM, 寄存器分配     │
│    ✅ 零新语法: 版本号即后缀, 无关键字, 无 block arg         │
│    ✅ VM 零变化: slot 复用保持不变, 版本号被忽略             │
│    ✅ 向后兼容: 不加版本号照常运行 (无优化)                  │
│                                                              │
│  这不是"用 ->/<- 替代 SSA"。                                 │
│  这是"把 SSA 的编译分析能力折叠进 ->/<- 的版本号系统中"。     │
│                                                              │
│  版本号 = SSA 的值身份                                      │
│  slot = 存储实体                                            │
│  合流版本号 = φ 的隐式编码                                   │
│  结构化控制流 = CFG 的确定性描述                              │
│                                                              │
│  deepxir 获得了:                                             │
│    执行层 = slot 复用的简洁                                  │
│    分析层 = SSA 的完整能力                                   │
│    转换层 = 编译器自动推导 (零人工介入)                       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
