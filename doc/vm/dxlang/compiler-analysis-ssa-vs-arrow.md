# `->`/`<-` 能否替代 SSA 做编译分析

> 本文分析 deepxir 的 `->`/`<-` 方向语义是否能在**不构建 SSA 的前提下**，直接支持经典编译器的分析和优化 pass。
> 结论：大部分可以，但有信息代价和精度损失。最优策略是局部直接分析 + 全局按需重建 SSA。

---

## 1. 问题定义

```
核心问题:
  给定一个 ->/<- 形式的 deepxir 函数:
    fn example(x: f32) -> y: f32 {
      x + 1.0 -> t1          ← t1 是 slot（可被改写）
      x * 2.0 -> t2          ← t2 是 slot
      t1 + t2 -> y           ← 读取 t1, t2
      ret y
    }

  能否在不转换为 SSA 的情况下:
  Q1: 判断 t1 和 t2 的值是否被后续使用？（死代码消除）
  Q2: 判断两处 x + 1.0 是否计算同一值？（公共子表达式消除）
  Q3: 判断 t1 在 y 处是否恒为常数值？（常量传播）
  Q4: 判断循环内 x * 2.0 是否可以提到循环外？（循环不变量外提）
  Q5: 构建干涉图做寄存器分配？
```

## 2. SSA 为什么天然适合编译分析

### 2.1 SSA 的结构性优势

```
SSA 的三个结构特性使编译器分析变得"廉价":

1. 单赋值 (Single Assignment)
   每个变量只有一个静态定义点。
   → use-def 链: 从使用点直接回溯到唯一定义点, O(1) 无歧义。

2. φ 节点 / block argument (控制流汇合)
   %y = block_arg(@then:%t, @else:%e)
   → 明确标注值可能来自哪些路径, 无需数据流分析。

3. 支配树 (Dominance Tree)
   定义点支配所有使用点。
   → 活性分析: 定义到最后一个使用的区间 = 干涉图的边。
   → 死代码: 无使用的定义 = 死代码。
```

### 2.2 `->`/`<-` 的结构性劣势

```
->/<- 的三个结构性问题:

1. 可变 slot (可多次赋值)
   x + 1.0 -> t1          ← 定义 t1 (第 1 次)
   ...
   x + 3.0 -> t1          ← 重定义 t1 (第 2 次)
   ...
   t1 * 2.0 -> y          ← 使用 t1 → 哪个定义？需要"到达定义分析"。

2. 无汇合标注
   分支内写 slot y:
   if flag {
     x + 1.0 -> y         ← 路径 A
   } else {
     x - 1.0 -> y         ← 路径 B
   }
   y * 2.0 -> result      ← y 来自 A 还是 B？
   → 需要迭代数据流分析才能确定 y 的来源集合。

3. 无内在支配关系
   ->/<- 不强制定义支配使用。
   可能出现"使用先于定义"的非法程序, 需要额外验证。
```

## 3. 逐个 Pass 分析

### 3.1 死代码消除 (DCE)

```
问题: 判断一条指令的结果是否"活着"（被后续使用, 或产生必要副作用）。

┌─── SSA ──────────────────────┐  ┌─── ->/<- ─────────────────────┐
│ %0 = add %x, %y              │  │ add(x, y) -> t0               │
│ %1 = mul %x, %y              │  │ mul(x, y) -> t1               │
│ ret %1                       │  │ ret t1                        │
│                              │  │                               │
│ 分析:                        │  │ 分析:                         │
│ %0 无 use → 死代码, 可删除    │  │ t0 后续无读取？→ 需检查 t0     │
│ O(1) 判定 (扫描 use 计数)     │  │ 是否在后续被读取。            │
│                              │  │ 如果 t0 从未被读 → 死代码      │
│                              │  │ 但需要:                       │
│                              │  │ 1. 确认 t0 无副作用 (无        │
│                              │  │    tensor.new/del 等)          │
│                              │  │ 2. 确认 t0 后续无读取          │
└──────────────────────────────┘  └────────────────────────────────┘

可行性: ✅ 可行, 但需额外步骤
  - SSA: 每个值有唯一名字 → 直接用 use 计数判断
  - ->/<-: 同一个 slot 可能在后续被重定义, 需要区分"本次定义的 t0"
    和"后续重定义的 t0"
  
  实现方法: liveness analysis (活性分析)
    对每个变量, 计算其定义-使用链。
    如果某个定义点后, 变量在被重定义前无任何读取 → 该定义是死的。
    
    算法复杂度: O(n²) 迭代到达定义 vs SSA 的 O(n)。
    但 deepxir 函数体通常很小 (<100 条指令), O(n²) 可接受。
```

### 3.2 公共子表达式消除 (CSE)

```
问题: 判断两个表达式是否计算同一值, 消除重复计算。

场景 A: 无干扰的重定义（简单情况）
  add(a, b) -> t1
  mul(c, d) -> t2        ← 不影响 a, b
  add(a, b) -> t3        ← 与第一条相同的表达式！但 t3 ≠ t1
                          ← 因为 t1 和 t3 是不同的 slot 名字
  此时 ->/<- 可以直接判断:
    "两个 add(a,b) 之间, a 和 b 都没有被重定义"
    → 它们是同一值, 可以消除。
    
  SSA 怎么做:
    %0 = add %a, %b
    %1 = mul %c, %d
    %2 = add %a, %b     ← SSA 直接看出 %a, %b 是同一个 SSA 值
                          → %0 和 %2 是同一值, 消除 %2, 用 %0 替代

场景 B: 有干扰的重定义（困难）
  add(a, b) -> t1
  add(c, 1.0) -> a      ← 重定义 a!!! 注意 -> 右边是 a
  add(a, b) -> t2       ← add(a, b) 但 a 已经被改过了
                         ← 这不是同一个计算！

  SSA 怎么做:
    %0 = add %a, %b
    %1 = add %c, 1.0    ← %1 不是 %a！是新 SSA 值
    %2 = add %1, %b     ← 操作数是 %1, 不是 %a → 自动判断为不同表达式

  ->/<- 怎么做:
    必须检查 add(a,b) 的两个出现之间, a 或 b 是否被重定义。
    → 这本质上是"到达定义 (reaching definitions)"分析。
    → 如果 a, b 的到达定义在两次 add 之间相同 → CSE 可消。
    → 如果不同 → 不可消。

可行性: ⚠️ 部分可行, 需要到达定义分析
  无干扰的线性代码段: 直接比较操作数和操作码 → CSE 可行。
  有控制流的代码段: 需要到达定义分析, 复杂度显著上升。
  
  对比 SSA: CSE 在 SSA 上是 O(1) 哈希查找。
  ->/<- 需要先做到达定义, 构建"值身份映射", 然后才能做 CSE。
  此时的到达定义结果, 本质上就是 SSA 的版本号。
```

### 3.3 常量传播 (Constant Propagation)

```
问题: 如果一个变量的值在编译期可知（常量）, 用常量替换它的使用。

场景: 简单常量传播
  constant(3.0) -> a
  a + 2.0 -> b
  b * 4.0 -> c
  ret c

  ->/<- 分析:
    1. a = 3.0 (常量)
    2. b = 3.0 + 2.0 = 5.0 (常量折叠)
    3. c = 5.0 * 4.0 = 20.0 (常量折叠)
    4. ret 20.0
    
  可行性: ✅ 线性代码段完全可行 (worklist 算法)

场景: 条件常量传播 (SCCP)
  a <- 3.0
  if cond {
    a <- 5.0             ← 重定义 a
  }
  ret a                  ← a 不是常量 (3.0 或 5.0, 取决于 cond)

  ->/<- 分析:
    在汇合点, a 的到达定义集合 = {3.0, 5.0}
    → 不是常量, 不能折叠。
    
  SSA 的 SCCP 更强大:
    利用支配关系, 可以证明某些路径不可达 → 常量传播更精确。
    ->/<- 可以做稀疏条件常量传播吗？
    可以, 但需要在 ->/<- 上重建支配树 + 到达定义。
    一旦重建了这些, 本质上就是在做 SSA 构造。

可行性: ✅ 基本常量传播可行, ⚠️ SCCP 精度略低于 SSA
  线性段: 完全等同 SSA。
  控制流汇合: 需要到达定义, 精度等同但需要额外计算。
  SCCP 的支配驱动精度: 需要重建支配信息, 与 SSA 构造等价。
```

### 3.4 复写传播 (Copy Propagation)

```
问题: 如果 y 只是 x 的别名 (y = x), 用 x 替代所有 y 的使用。

  x + 1.0 -> y
  y + 2.0 -> z       ← y 是 x 的复写？不！y = x + 1.0, 不是复写。
  ret z

  真正的复写:
  x -> y              ← y 就是 x 的值 (identity copy)
  y + 2.0 -> z        ← 可以用 x 替代 y
  ret z

  ->/<- 分析:
    检测 "op(args) -> name" 中 op 是 identity 或 name 只是另一个变量的别名。
    在 ->/<- 中: x -> y 等价于 "把 x 的值写入 slot y"。
    
    SSA: %y = %x → 直接替换所有 %y 的 use 为 %x。
    ->/<-: 需要确认从 y 的定义到使用之间, x 没有被重定义。
          → 又是到达定义问题。

可行性: ✅ 可行, 同样需要到达定义检查
```

### 3.5 全局值编号 (GVN)

```
问题: 给每个"计算出的值"分配唯一编号, 相同编号 = 相同值。

  这是 CSE 的泛化: 不仅检测相同的表达式, 还检测等价但形式不同的表达式。
  例如: (a + b) + c  和  a + (b + c)  在加法可结合时等价。

  SSA 的 GVN:
    每个 SSA 值有一个编号。
    两值编号相同 → 值等价 → 可以替换。
    SSA 的 use-def 结构让编号传播变得简单: 从叶子(常量/参数)向上传播。
    
  ->/<- 的 GVN:
    同样需要对每个 slot 的"当前值"进行编号。
    但 slot 可能被重定义, 编号会变化。
    需要在每个程序点维护 "slot → 值编号" 的映射。
    
    这本质上等价于:
    1. 做 SSA 构造 (给每个 slot 的每次定义分配版本号)
    2. 在 SSA 上做 GVN
    3. 结果映射回 ->/<- (可选)

可行性: ❌ 直接做极困难, 需先重建 SSA
  GVN 的核心是"值相等"判断, 而 ->/<- 的核心是"存储位置"。
  没有"值身份"概念, GVN 的编号没有附着对象。
  必须先做 SSA 构造, 为每个定义点生成值身份, 再做 GVN。
```

### 3.6 循环不变量外提 (LICM)

```
问题: 将循环内不随迭代变化的值计算移到循环外。

  for i in 0..n {
    x * 2.0 -> t         ← x 在循环内不变？t 是循环不变量？
    t + i -> y           ← 但 x 在循环外可能被重定义...
  }

  ->/<- 分析:
    判断一条指令是否循环不变量:
    1. 操作数是常量
    2. 或操作数来自循环外的定义
    3. 或操作数是循环不变量

    在 ->/<- 中, 需要:
    - 识别循环边界 (for/while 关键字 → 天然有)
    - 做到达定义分析: 每个操作数的定义点在循环内还是外？
    - 迭代不动点: 循环不变量集合可能逐步扩大
    
    这完全可行, 只是需要到达定义。

可行性: ✅ 可行, 需要到达定义 + 循环识别
  deepxir 的 for/while 关键字天然标注了循环边界 → 比原始字节码容易。
  到达定义分析后, 标准 LICM 算法可以直接应用。
```

### 3.7 寄存器分配 / 干涉图构建

```
问题: 将无限虚拟寄存器映射到有限物理寄存器。

  SSA 的做法:
    1. 活性分析 → 干涉图 (两变量活性区间重叠 → 不能共寄存器)
    2. 图着色
    3. SSA 解构 (插入 copy 指令断开干涉边)
    
  ->/<- 的做法:
    变量名字就是存储 slot。
    干涉图 = 两个 slot 的活性区间是否重叠。
    活性分析 = 从定义点到最后一个使用的区间。
    这个分析在 ->/<- 上同样可以做: 扫描每个变量, 找其所有定义点和所有使用点。
    
    关键差异:
    SSA: 每个 SSA 值的活性区间精确 (唯一定义点 → 最后一个使用)。
    ->/<-: 同一个名字可能有多段活性区间 (被重定义多次)。
          需要为每个定义点单独计算活性区间。
          
    示例:
    x + 1.0 -> t       ← t 定义点 1, 活性: 指令1 → 读取点
    t * 2.0 -> y       ← 读取 t (定义点1的 t 的最后使用)
    ...
    x + 3.0 -> t       ← t 定义点 2 (重定义), 活性: 指令k → ...
    t + 4.0 -> z       ← 读取 t (定义点2的 t)

    干涉图需要区分 t_v1 和 t_v2 —— 这就是在做 SSA 构造！

可行性: ⚠️ 基本可行, 但精确版本 = SSA 构造
  粗略寄存器分配: 把整个变量 t 当作一个分配单元 → 可能过度保守。
  精确寄存器分配: 需要区分 t 的不同版本 → 本质上是 SSA 构造。
```

### 3.8 归纳变量识别与强度削弱

```
问题: 识别循环中的归纳变量 (如 i = i + 1), 并用更廉价的操作替代。

  for i in 0..n {
    i * 4 -> offset      ← offset 是 i 的线性函数
    load(base + offset)  ← 可以用迭代的 base 指针替代乘法
  }
  
  ->/<- 分析:
    检测循环内变量的更新模式。
    i -> i+1 是归纳变量。
    offset -> i*4 是派生归纳变量。
    
    这类分析依赖的是循环结构和变量间的定义-使用关系,
    不依赖 SSA。标准的 reaching definitions 足够。

可行性: ✅ 可行, 不依赖 SSA
  归纳变量检测是模式匹配, 检查循环内的赋值模式即可。
```

## 4. 汇总对比

| Compiler Pass | SSA 直接 | `->`/`<-` 直接 | 需要额外什么 | 精度损失 |
|---------------|---------|---------------|-------------|---------|
| **死代码消除 (DCE)** | O(n) use 计数 | O(n²) 活性分析 | 到达定义 | 无 |
| **常量折叠** | 直接替换 | 直接替换 | 无（线性段） | 无 |
| **常量传播** | worklist O(n) | worklist O(n²) | 到达定义 | 轻微（边角情况） |
| **SCCP** | 支配驱动, 精度最高 | 需要支配树 | 支配树 + 到达定义 | 有（缺失不可达路径剪枝） |
| **复写传播** | O(n) | O(n²) | 到达定义检查 | 无 |
| **CSE** | O(1) 哈希 | O(n²) 到达定义 | 到达定义 | 无（线性段），有（控制流） |
| **GVN** | O(n³) 但不需 SSA 构造 | ❌ 不可行 | 需先 SSA 构造 | — |
| **LICM** | 支配树 + 到达定义 | 循环边界 + 到达定义 | 到达定义 | 无 |
| **归纳变量** | 模式匹配 | 模式匹配 | 无 | 无 |
| **寄存器分配** | 活性区间精确 | 需区分变量版本 | 到达定义 | 有（粗略分配） |
| **内联** | 参数替换 | 参数替换 | 无 | 无 |
| **函数特化** | use-def 遍历 | slot 扫描 | 无（简单版） | 有 |

**关键观察**: 几乎所有需要显著额外工作的地方，额外工作就是"到达定义分析"。
而到达定义分析的结果，就是给每个 slot 的每次定义分配一个"版本号"——这已经在做 SSA 构造。

## 5. 理论等价性

### 5.1 到达定义 = SSA 构造

```
定理:
  对 ->/<- 程序做"到达定义分析 (Reaching Definitions Analysis)",
  其输出等价于给程序做"裁剪 SSA 构造 (Pruned SSA Construction)"。

  证明草图:
  1. 到达定义分析: 对每个程序点 p 和每个变量 v,
     计算哪些 v 的定义点可以到达 p。
     
  2. 如果 p 处使用 v, 且只有一个定义点 d 到达 p,
     则 use-def 链: p 处使用 v → d 处的定义。
     
  3. 如果有多个定义点到达 p (控制流汇合),
     需要插入 φ 节点或 block argument。
     
  4. 对所有变量重复 → 得到完整的 SSA 形式。
  
  这是标准的 SSA 构造算法 (Cytron et al. 1991) 的变体。
```

### 5.2 编译器分析的信息需求层次

```
Level 0: 局部分析（基本块内）
         → ->/<- 直接可用, 无需任何额外信息。

Level 1: 全局但无控制流汇合（单路径）
         → ->/<- + 简单的定义扫描即可。

Level 2: 全局有控制流汇合（多路径）
         → 需要到达定义分析 = 需要 SSA 构造。
         → 此时 ->/<- vs SSA 的区别 = 是否预计算 use-def 链。

Level 3: 值等价性分析 (CSE, GVN, SCCP)
         → 需要值身份 → 必须 SSA (或等价结构)。
         → 没有 SSA 就没有"值"这个概念, 只有"slot"。

Level 4: 高级变换 (向量化, 循环变换, 自动并行)
         → 需要完整的 use-def + 依赖分析 → SSA 是前提。
```

## 6. deepxir 的实践建议

### 6.1 分层策略

```
┌─────────────────────────────────────────────────────────────┐
│                   deepxir 编译器优化分层                     │
│                                                             │
│  Layer 0: 轻量 Pass（永远直接做, 不建 SSA）                  │
│  ┌─────────────────────────────────────────────────┐      │
│  │ • 常量折叠 (const folding)                       │      │
│  │ • 代数化简 (algebraic simplification)            │      │
│  │ • 死指令消除 (peephole DCE)                      │      │
│  │ • 内联 (inline)                                  │      │
│  │ • 中缀展开 (infix→prefix)                        │      │
│  │                                                  │      │
│  │ 实现: 逐条扫描指令, 维护 slot→value 简单映射     │      │
│  │ 代价: O(n)                                       │      │
│  │ 精度: 等同 SSA (线性段)                          │      │
│  └─────────────────────────────────────────────────┘      │
│                                                             │
│  Layer 1: 中等 Pass（按需建 SSA, 用完即弃）                 │
│  ┌─────────────────────────────────────────────────┐      │
│  │ • 死代码消除 (global DCE)                        │      │
│  │ • 公共子表达式消除 (CSE)                         │      │
│  │ • 复写传播 (copy propagation)                    │      │
│  │ • 循环不变量外提 (LICM)                          │      │
│  │ • 常量传播 (constant propagation + SCCP)         │      │
│  │                                                  │      │
│  │ 实现: 构建 pruned SSA → 运行标准算法 → 解构 SSA │      │
│  │ 代价: SSA 构造 O(nα(n)) + pass + 解构 O(n)      │      │
│  │ 精度: 等同 SSA                                   │      │
│  └─────────────────────────────────────────────────┘      │
│                                                             │
│  Layer 2: 重型 Pass（C2 Scheduler 专属）                    │
│  ┌─────────────────────────────────────────────────┐      │
│  │ • 全局值编号 (GVN)                               │      │
│  │ • 向量化                                        │      │
│  │ • 循环变换                                      │      │
│  │ • GPU kernel fusion                             │      │
│  │                                                  │      │
│  │ 实现: 全 SSA + 支配树 + 依赖分析                 │      │
│  │ 代价: 昂贵, 但只在 Scheduler 离线做              │      │
│  └─────────────────────────────────────────────────┘      │
│                                                             │
│  Layer 3: 执行（不建 SSA）                                  │
│  ┌─────────────────────────────────────────────────┐      │
│  │ VM 直接解释 ->/<- 指令                           │      │
│  │ 零额外开销                                       │      │
│  └─────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 SSA 按需构造的成本

```
给定一个 N 条指令、V 个变量的 ->/<- 函数:

SSA 构造 (Cytron 算法):
  1. 计算支配树:       O(N log N) 或 O(N α(N))
  2. 计算支配边界:     O(N)
  3. 插入 φ 节点:      O(V × 支配边界)
  4. 变量重命名:       O(N)
  
  总计: O(N α(N)) ~ O(N log N) 在实践中

对于 deepxir 场景 (函数通常 < 200 条指令):
  SSA 构造开销 < 1ms
  → 按需构建完全可接受

结论: 不要因为害怕 SSA 构造的成本而避免它。
      但也不要为了所有优化都建 SSA。
      "需要时再建" 是最优策略。
```

### 6.3 推荐实现路线

```
Phase 1 (当前 → C1 阶段):
  仅做 Layer 0 pass。
  VM 直接解释, 无 SSA。
  优化: 常量折叠 + 代数化简 + peephole DCE。
  实现复杂度: 低。

Phase 2 (C2 Scheduler):
  实现 Layer 1 pass。
  Scheduler 接收 ->/<- IR → 按需构建 SSA → 优化 → 解构 SSA → 输出基本块 IR。
  实现复杂度: 中。

Phase 3 (高级优化):
  实现 Layer 2 pass。
  仅在有明显收益时启用 (如 kernel fusion 可减少 GPU 启动开销时)。
  实现复杂度: 高。
```

## 7. MLIR 的佐证

MLIR 的架构选择验证了上述分析：

```
MLIR 的 dialect 栈:
  scf.for / scf.if       ← 结构化控制流 (类比 deepxir if/for/while)
    │  lower
    ▼
  cf.br / cf.cond_br     ← 底层控制流 + block argument (SSA)
    │  在此层做优化 (CSE, DCE, LICM, ...)
    ▼
  llvm.func / arith      ← 更低层
    │
    ▼
  LLVM IR (完整 SSA)

MLIR 的选择:
  ✅ 前端输出结构化 scf (人可读, 易生成)
  ✅ lowering 到 cf + block argument (SSA, 可优化)
  ✅ 再 lower 到 LLVM IR (成熟优化基础设施)
  ❌ 不在 scf 层做全局优化
  ❌ 不在 ->/<- 语法层做值等价分析

deepxir 的对应:
  Layer 1: if/for/while + ->/<-  =  scf dialect
  Layer 2: 基本块 + SSA          =  cf dialect  
  Layer 3: 后端执行              =  GPU kernel
```

## 8. 最终结论

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  Q: ->/<- 能否替代 SSA 做编译分析？                           │
│                                                              │
│  A: 取决于分析层次。                                          │
│                                                              │
│  ✅ 局部分析 (基本块内):                                      │
│     完全可以, ->/<- 直接可用, 零额外成本。                    │
│     常量折叠、代数化简、peephole 优化都是 O(n)。             │
│                                                              │
│  ⚠️ 全局分析 (跨基本块, 有控制流):                            │
│     部分可行, 但需要到达定义分析。                            │
│     到达定义分析的结果 = SSA 构造的等价物。                   │
│     此时 ->/<- 和 SSA 的边界模糊——你在"隐式"做 SSA。         │
│                                                              │
│  ❌ 值等价分析 (CSE, GVN, SCCP):                              │
│     不可行。没有"值身份"概念, 无法判断两值是否相同。          │
│     必须先显式构建 SSA。                                      │
│                                                              │
│  最优策略:                                                    │
│  1. 永远不建 SSA: 局部优化 (Layer 0)                          │
│  2. 按需建 SSA: 全局优化 (Layer 1)                            │
│  3. 总是建 SSA: 高级变换 (Layer 2, Scheduler 离线)            │
│                                                              │
│  核心洞见:                                                    │
│  "->/<- 能否替代 SSA" 这个问题本身就是倾斜的。                │
│  正确的问法是: "在 ->/<- 上做编译器分析，哪些层次不需要       │
│  SSA，哪些层次本质就是 SSA 构造的另一种叫法？"                │
│                                                              │
│  答案: 局部优化不需要 SSA。                                   │
│        全局优化需要 SSA，无论是显式构建还是隐式等价于它。     │
│        高级优化必须 SSA。                                     │
│                                                              │
│  而 SSA 构造的成本 (O(N log N)) 在 deepxir 的规模下 (<200     │
│  条指令/函数) 完全可忽略 (<1ms)，所以需要时就用，               │
│  不需要时也别没事找事。                                       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 9. 变量版本号方案分析

> **问题**：如果对 `->`/`<-` 中的变量增加版本后缀 (`x/0`, `x/1`, `x/2`...)，每次写入递增版本号，能否替代 SSA 做编译分析的全部需求？

### 9.1 方案定义

```
规则:
  1. 每个变量有一个版本计数器，初始为 0
  2. 每次出现在 -> 右侧（被写入），版本号 +1
  3. 每次出现在 -> 左侧（被读取），使用当前可见的最新版本号
  4. 版本号作为变量名的后缀: x/0, x/1, x/2, ...

示例:
  constant(3.0) -> x/0       ← x 首次写入 → 版本 0
  x/0 + 2.0 -> y/0           ← 读取 x/0, 写入 y/0
  y/0 * 4.0 -> z/0           ← 读取 y/0, 写入 z/0
  constant(5.0) -> x/1       ← x 第二次写入 → 版本 1（新身份）
  x/1 + 1.0 -> w/0           ← 读取 x/1（不是 x/0）
  ret w/0
```

### 9.2 能解决什么

```
✅ 死代码消除 (DCE)
  x/0 + 2.0 -> y/0          ← y/0 后续有使用吗？
  扫描所有指令的读侧: 出现 y/0? → 有则活, 无则死。
  版本号让每个定义有唯一标识 → 用 use 计数即可, O(n)。
  对比无版本: 需要区分"本次定义的 y"和"后续重定义的 y"。
  
  示例: 无版本时的问题
    add(a, b) -> y           ← 定义 y
    add(a, b) -> z
    mul(c, d) -> y           ← 重定义 y！（新值, 旧名字）
    ret z
    无版本: 扫描 y 的使用 → 发现 y 在 line 1 和 line 3 出现
            但 line 1 的 y 和 line 3 的 y 是不同的值
            必须做活性分析才能判定 line 1 的 y 是否死代码
  
  有版本时:
    add(a, b) -> y/0         ← y/0: 唯一定义
    add(a, b) -> z/0
    mul(c, d) -> y/1         ← y/1: 新定义, 新身份
    ret z/0
    y/0 后续无使用 → 死代码, 直接删除。O(1) 判定。

✅ 公共子表达式消除 (CSE)
  add(a/0, b/0) -> t1/0
  mul(c/0, d/0) -> u/0      ← 不影响 a, b 的版本
  add(a/0, b/0) -> t2/0     ← 同样读取 a/0, b/0 → 同一表达式!
  
  版本号直接暴露操作数的"值身份":
  - 两次 add 都读取 a/0 和 b/0
  - 两次 add 之间 a 和 b 的版本没有变化 (没有 a/1, b/1)
  - → 两次 add 计算同一值 → CSE 可消除 t2/0, 替换为 t1/0
  
  对比无版本:
    add(a, b) -> t1
    add(a, b) -> t2         ← 无法判断 t1 == t2
    因为 a 可能在第一条指令后被重定义（写成 a <- ...）
    需要到达定义分析才能确认

✅ 全局值编号 (GVN)
  版本号 = 值编号。每个版本号标识一个唯一的值。
  
  add(a/0, b/0)   → 值编号 = (add, a/0, b/0)
  mul(t1/0, 2.0)  → 值编号 = (mul, t1/0, 2.0)
  
  GVN 算法: 从叶子版本(参数, 常量)向上计算哈希 → 相同哈希 = 相同值。
  版本号天然就是 GVN 的节点标识。

✅ 复写传播
  x/0 -> y/0               ← y/0 是 x/0 的复写
  y/0 + 2.0 -> z/0         ← 可以用 x/0 替代 y/0 → x/0 + 2.0 -> z/0
  
  版本号让复写关系显式: y/0 的定义就是 x/0 的值。
  检查 x 版本在 y/0 的使用点未被重定义 → 安全替换。

✅ 到达定义分析 — 版本号让分析退化为简单查找
  无版本: 到达定义需要迭代数据流分析 O(n²)
  有版本: 在指令 i 处读 x/k, 直接找定义 x/k 的指令 → O(1)
```

### 9.3 不能解决什么：φ 缺口

```
版本号方案的根本局限: 控制流汇合 (Control Flow Join)

问题场景:
  fn merge_example(flag: bool, a: f32) -> y: f32 {
    if flag {
      a/0 + 1.0 -> x/0           ← 路径 A: 定义 x/0
    } else {
      a/0 - 1.0 -> x/1           ← 路径 B: 定义 x/1
    }
    x/? * 2.0 -> y/0             ← 合并点: 使用 x 的哪个版本？?
  }

困境:
  在合并点, x 可能是 x/0 (走 then 分支) 或 x/1 (走 else 分支)。
  使用 x/0 不对 (else 路径会读错), 使用 x/1 也不对 (then 路径会读错)。
  
  需要一个新版本 x/2 来表示 "x/0 或 x/1", 这就是 φ 节点:
    x/2 = φ(x/0, x/1)           ← ⚠️ 这已经超出"纯版本号"方案了
  
  SSA 的解决: block argument
    @merge(%x: f32):            ← %x 是 block 参数, 等价于 φ(x/0, x/1)
      %x * 2.0 -> %y
    
  ->/<- (无版本) 的解决: slot 复用
    if flag { a + 1.0 -> x }    ← 写入 slot x
    else    { a - 1.0 -> x }    ← 写入 slot x (同一 slot)
    x * 2.0 -> y                ← 读 slot x → 无论哪个分支, 值都在里面
    VM 直接读 slot, 不需要 φ。
  
  版本号的尴尬:
    版本号想要"值身份", 但 slot 不复用就没有"身份"——
    不同路径写入不同 slot, 合流时不知道该读哪个。
    要解决就必须引入 φ 节点或 block argument → 这就是在做 SSA 构造。
```

### 9.4 版本号 + slot 复用：混合方案

```
核心思路: 版本号作为编译器元数据, slot 作为执行层实体。
        两者分离, 各司其职。

  if flag {
    a/0 + 1.0 -> x/0      ← 版本号供编译器分析, slot x 供 VM 执行
  } else {
    a/0 - 1.0 -> x/1      ← 版本号供编译器分析, slot x 供 VM 执行
  }
  
  编译器视角:
    合并点处, slot x 的可能版本集合 = {x/0, x/1}
    → 编译器做分析时, 将 x 当作 "值 = x/0 ∨ x/1"
    → 如果要做精确 CSE/GVN 需要 φ: x/2 = φ(x/0, x/1)
    
  VM 视角:
    合并点处, 读 slot x → 得到实际值 (运行时确定)
    → VM 不需要知道版本号, 版本号只是编译器的"注释"

优点:
  - VM 执行层零变化 (slot 复用不变)
  - 版本号加速编译器分析 (线性段 O(1))
  - 不需要 φ 节点来执行, 只需要 φ 节点来优化

缺点:
  - 版本号和 slot 的两套命名需要同步
  - 仍需要 SSA 构造来生成 φ (版本号本身不生成 φ)
  - 本质是两套系统的叠加, 增加实现复杂度
```

### 9.6 φ 缺口为什么无法绕过

```
本质原因: 控制流汇合引入了"不确定性", 而值身份要求"确定性"。

  确定性要求 (值身份):
    "x 在合并点的值"必须有一个唯一标识。

  不确定性来源 (控制流):
    "x 在合并点的值"取决于实际执行路径。
    路径 A: x = expr1
    路径 B: x = expr2

  矛盾:
    值身份需要唯一标识 → 需要一个新名字 (x/3)
    但 x/3 的值不是计算出来的 → 它是"选择"出来的
    → 这个"选择"就是 φ 节点的语义

  三种做法本质上都在解决这个矛盾:

  1. Slot 复用 (纯 ->/<-):
     回避矛盾——不给 x 值身份, 只给 x 存储位置。
     "x 在合并点的值"没有标识, 只有"slot x 的内容"。

  2. φ 节点 (纯 SSA):
     直面矛盾——创建一个新标识 x/3, 明确标注其来源 {x/1, x/2}。
     φ 是"值选择器", 语义是"根据控制流选择 x/1 或 x/2"。

  3. Block argument (MLIR SSA):
     重新表述矛盾——把"选择"变成"参数化"。
     合并 block 接受一个参数, 调用者传入不同值。
     "这是 x 的值, 我不关心它从哪来, 只关心它是 f32 类型"。

  版本号方案避不开这个矛盾。
  版本号让每个 slot 的每次写入有了身份,
  但合流时依然面临"多个身份汇入一个使用点"的问题。
  版本号没有提供解决这个问题的原语。
```

### 9.7 版本号的实际价值：加速 SSA 构造

```
版本号真正的威力不在于"替代 SSA", 而在于"加速 SSA 构造"。

标准 SSA 构造 (Cytron 算法) 的三个步骤:
  1. 支配树        → O(N log N)   ← 需要
  2. 支配边界       → O(N)         ← 需要
  3. 变量重命名     → O(N)         ← 版本号方案直接跳过!

版本号的贡献:
  标准算法中, "变量重命名"步骤需要:
    对每个变量维护版本栈 (push 新版本 / pop 旧版本)
    遍历支配树, 在每个基本块做重命名

  如果 ->/<- 已经带有版本号:
    变量重命名步骤直接跳过
    每个定义的版本号已经显式标注
    use-def 链已经存在（从读侧的版本号直接查到写侧的定义点）
    
    只剩下:
      1. 支配树        → 需要
      2. 支配边界      → 需要
      3. 插入 φ 节点   → 需要 (这是无法绕过的)
      4. ~~变量重命名~~ → 跳过!

  节省: 约 25-40% 的 SSA 构造时间。
  但关键瓶颈 (支配树) 依然存在。
```

### 9.8 实践判断

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  变量版本号能否替代 SSA 做编译分析的全部需求？                 │
│                                                              │
│  A: 不能。版本号填补了"值身份"的缺口,                        │
│     但无法填补"控制流汇合"的 φ 缺口。                        │
│                                                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                                                     │   │
│  │  版本号的贡献边界:                                    │   │
│  │                                                     │   │
│  │  ✅ 线性段分析: 完全替代 SSA, 甚至更简单             │   │
│  │     DCE / CSE / constant prop / GVN / copy prop      │   │
│  │     全部 O(n), 无 φ 构造开销                         │   │
│  │                                                     │   │
│  │  ⚠️ 全局分析: 加速 SSA 构造, 但不取代                │   │
│  │     use-def 链已存在 → 跳过变量重命名步骤            │   │
│  │     但仍需支配树 + 支配边界 → 生成 φ                 │   │
│  │                                                     │   │
│  │  ❌ 替代 φ: 不可能的                                │   │
│  │     φ 是控制流汇合的必然产物,                        │   │
│  │     版本号是值身份的原语, φ 是值选择的原语,           │   │
│  │     它们是正交概念, 不是替代关系。                   │   │
│  │                                                     │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                              │
│  对 deepxir 的建议:                                           │
│                                                              │
│  方案 A (当前, 无版本): 最简执行, 最弱分析                    │
│    → 适合 C1 阶段 (VM 直接解释, 不做优化)                    │
│                                                              │
│  方案 A+ (版本号作为可选元数据):                               │
│    → 前端可选地在 -> 右侧附加版本号                           │
│    → Scheduler 读取版本号加速 SSA 构造                        │
│    → VM 忽略版本号 (只看 slot 名)                            │
│    → 不增加 VM 复杂度, 但给编译器开了后门                    │
│                                                              │
│  方案 C (版本号 + slot 复用 = 双轨):                          │
│    → 两套命名系统, 实现复杂, 可读性差                        │
│    → 仅在优化收益明确时引入 (Phase 3)                        │
│                                                              │
│  推荐: 保持当前纯 slot 方案。                                 │
│        当 Scheduler 优化成为瓶颈时,                             │
│        在前端输出中附加版本号作为编译提示,                     │
│        Scheduler 用版本号加速 SSA 构造 (跳过多余步骤).        │
│        VM 完全不受影响。                                      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
